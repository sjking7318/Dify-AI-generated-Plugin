# AI 生成工作流 · 插件工具增强 — 完整设计与实现说明

分支：`feature/workflow-copilot-plugin-schema`（基于 `feature/workflow-copilot` 本地新建）

这份文档讲清楚三件事：
1. AI 生成工作流的整体流程（三个阶段）到底怎么运作；
2. 本次为「插件工具节点」做的增强——外部插件信息怎么获取、怎么组合进生成、怎么适配节点结构；
3. 一路排查出来的连线 / 变量 / 结构问题各自怎么修的。

全程用大白话，尽量不用术语；出现的专有名词第一次都会解释。

---

## 第一部分：先搞懂「AI 生成工作流」是怎么回事

### 1.1 一句话概括

你在界面上用自然语言描述一个需求（例如「拉取 GitHub 仓库的 issue，分类后生成报告」），系统就自动画出一张可以直接运行的工作流程图（节点 + 连线），你确认后一键应用到画布。

### 1.2 为什么要分三个阶段

最朴素的做法是「让大模型一次性把整张图吐出来」。但整张图是很大的 JSON（几十个节点、每个节点几十个字段、还有连线和坐标），一次性生成又慢又容易出错——模型经常写错字段、连错线、漏掉必填项。

所以这里把生成拆成三个阶段，每个阶段只干一件小事，越小越可靠：

```
你的自然语言需求
      │
      ▼
┌─────────────┐   阶段一：规划（Planner）
│  Planner    │   只决定「要哪几个节点、谁连谁」，不填任何细节
└─────────────┘
      │  产出一个「骨架」：节点清单 + 连线清单
      ▼
┌─────────────┐   阶段二：并行装配（Node Builders）
│  Builders   │   每个节点单独交给模型，填它自己的详细配置
└─────────────┘   多个节点同时进行（并行），快
      │  产出每个节点的「配置块」
      ▼
┌─────────────┐   阶段三：组装 + 修复 + 校验（Postprocess）
│ Postprocess │   用代码把碎片拼成整图，修正模型的错误，最后检查
└─────────────┘
      │
      ▼
一张结构合法、可以直接存进草稿的工作流图
```

关键理念有两条：
- **模型只出主意，代码来兜底。** 模型负责「语义」（这个流程该有哪些步骤、每步大概怎么配），但模型产出的东西默认「是不可靠的」；所有确定性的事情（改 ID、算坐标、修连线、对齐变量名）都由代码强制修正。
- **两个入口，同一套核心。** cmd+k 的 `/create`·`/refine`（一次性生成）和 Copilot 面板（多轮对话生成）是两个入口，但底层都调用同一段生成核心，行为完全一致。

### 1.3 分层：谁负责什么

| 层 | 位置 | 职责 |
|---|---|---|
| 控制器（Controller） | `api/controllers/console/app/generator.py`、`copilot.py` | 接收 HTTP 请求、校验入参、把结果按 SSE 流式返回、把异常翻译成前端能懂的错误 |
| 服务层（Service） | `api/services/workflow_generator_service.py`、`workflow_copilot_service.py` | 准备生成所需的「外部数据」（模型实例、已装工具信息），注入给核心 |
| 核心（纯逻辑） | `api/core/workflow/generator/runner.py` | 三阶段流水线本体。**不碰数据库、不碰租户、不碰插件服务**，所有外部数据都由服务层当参数传进来 |
| 提示词 | `api/core/workflow/generator/prompts/` | 给模型的指令（planner / builder 两套） |
| 类型 | `api/core/workflow/generator/types.py` | 所有数据结构的定义 |
| 工具信息 | `api/core/workflow/generator/tool_catalogue.py`、`tool_schema.py` | 获取「这个租户装了哪些工具」及「某个工具的详细参数」 |

**核心为什么要「纯」**：因为它要被单元测试、要被两个入口复用，如果它自己去连数据库/插件服务，就没法独立测试、也会和基础设施耦合。所以约定：核心需要的任何外部数据，都由服务层先查好、当函数参数传进去。

## 第二部分：本次要解决的核心问题——插件工具节点

### 2.1 问题背景

工作流里有一类节点叫「工具（tool）节点」，它调用一个已安装的插件工具（比如 GitHub 插件的「拉取仓库 issue」、网页抓取插件的「抓取网页」）。

**改动前，工具节点是这么生成的：**
- 阶段一（Planner）能看到的工具信息，只有一份「清单」：每个工具一行，格式是 `工具名 — 一句话描述`。够用来「选哪个工具」，但**没有参数信息**。
- 阶段二（Builder）配置工具节点时，用的是一段**写死的通用模板**——它只知道工具节点这个「壳」大概长什么样（有 provider_id、tool_name、tool_parameters 这些字段），但**完全不知道这个具体插件到底有哪些参数、参数叫什么、什么类型、哪些必填**。

结果就是：模型只能凭猜测填参数名，经常填错、漏必填、类型不对，生成出来的工具节点一运行就报错。而且那段通用模板还把工具类型写死成 `builtin`（内置），对插件工具是错的（插件应该是 `plugin`）。

### 2.2 为什么不能「把所有工具的详细参数一次性都给 Planner」

一个租户可能装了几十上百个插件，每个插件又有几十个参数。如果把所有工具的完整参数都塞进 Planner 的提示词，会瞬间撑爆大模型的上下文窗口（输入长度上限）。这也是为什么那份「清单」本身就要截断到最多 80 条。

### 2.3 解决思路：渐进式（延迟）加载

把工具信息分成**两级**，在**两个不同时机**分别获取：

| | 第一级（轻） | 第二级（重） |
|---|---|---|
| 获取什么 | 工具名 + 一句话描述 | 这个工具的**详细参数清单** |
| 给谁用 | Planner（用来选工具） | 被选中工具的那个 Builder（用来填参数） |
| 什么时候 | 生成一开始，全量预取 | Planner **选定**某工具**之后**，按需现拉 |
| 数据量 | 每工具一行，截断 80 条 | 只拉被选中的那几个工具 |

打个比方：第一级像「菜单」——只列菜名和简介，帮你点菜；第二级像「详细配方」——你点了哪道菜，才去厨房拿那道菜的配方。不会一上来把所有配方都堆你面前。

这就是「渐进式加载」：**不是一开始全量加载，而是等真正需要（Planner 选中）时才加载那一份详细信息。**

## 第三部分：外部插件信息是怎么获取的（关键事实）

要做上面的第二级，必须搞清楚「插件的参数到底存在哪、怎么拿」。这里有几个反直觉但很重要的事实（都已核对源码）：

### 3.1 「租户装了哪些插件」不在业务数据库里

Dify 的后端业务数据库里**没有一张表**记录「这个租户装了哪些插件」。这份清单存在一个独立的服务——**插件守护进程（plugin daemon）**里，后端每次都通过 HTTP 去问它。

- 枚举已装工具的入口：`ToolManager.list_builtin_providers(tenant_id)`
  - 内置工具：扫本地磁盘目录（和租户无关）；
  - 插件工具：`PluginToolManager.fetch_tool_providers(tenant_id)` → 请求 daemon 的 `management/tools` 接口。

### 3.2 拿某个工具「详细参数」的现成入口

正常情况下，你在画布上拖一个工具节点、选中某个工具时，前端会渲染出这个工具的参数表单——它调的就是这个现成接口，我们直接复用：

- `BuiltinToolManageService.list_builtin_tool_provider_tools(tenant_id, provider)`
  - 传入：租户 ID + provider 标识；
  - 返回：该 provider 下所有工具，每个工具带一个 `parameters` 列表和一个 `output_schema`（输出结构）。

每个参数（`ToolParameter`）里我们关心这些字段：

| 字段 | 含义 |
|---|---|
| `name` | 参数名 |
| `type` | 类型：string / number / boolean / select / file / … |
| `required` | 是否必填 |
| `default` | 默认值 |
| `options` | 如果是 select，可选值有哪些 |
| `llm_description` / `human_description` | 参数说明 |
| **`form`** | **最关键**：这个参数由谁来填（见下） |

### 3.3 `form` 字段——决定「哪些参数需要在节点里填」

`form` 有三个取值，直接决定生成工具节点时该不该给这个参数填值：

- `form`（表单）：**用户/生成器要在节点上填好的**——这些才需要写进节点的 `tool_parameters`；
- `llm`：运行时由智能体/大模型自己填的——**不写进**节点的静态配置，但要告诉生成器「别碰这个」；
- `schema`：安装期的元信息——直接忽略。

过去完全没区分这个，导致模型把所有参数（包括本该运行时填的、本该忽略的）胡乱填一通。本次严格按 `form` 区分。

### 3.4 provider 标识的格式（一个大坑）

- **插件工具**：`provider_type = "plugin"`；`provider_id` 是**三段式**，形如 `langgenius/github/github`（组织 / 包 / provider 名）。
- **内置工具**：`provider_type = "builtin"`；`provider_id` 是纯名字，如 `time`、`webscraper`。

Dify 校验插件 ID 时，只认三段式。如果被截断成两段 `langgenius/github`，就会报 `Invalid plugin id` 并导致画布崩溃——这正是本次踩到的一个真实 bug（见 5.2）。

### 3.5 工具节点的数据结构（生成目标）

工具节点的 `data` 里，参数是这样组织的：`tool_parameters` 是一个字典，`{参数名: {type, value}}`，其中 `type` 有三种：
- `constant`：常量，value 是字面量；
- `variable`：变量引用，value 是 `["上游节点id", "字段名"]`；
- `mixed`：混合字符串，value 里含 `{{#节点id.字段#}}` 这样的占位符。

生成器要按 3.2 拿到的参数清单，把 `form` 类参数逐个填成上面这种 `{type, value}` 结构。

## 第四部分：三阶段里，插件工具是怎么被「组合、适配」进去的

现在把第二部分的思路，落到三阶段的每一步。

### 4.1 数据流总览

```
你的需求
  │
  ▼
[服务层] 准备三样东西：
  · 模型实例
  · 工具清单文本（轻，给 Planner）           ← tool_catalogue
  · 工具详细参数解析器（一个回调函数）        ← tool_schema  ★本次新增
  │
  ▼
[阶段一 Planner] 看「工具清单文本」→ 选工具
  产出节点：{类型:"tool", provider:"langgenius/github/github", tool:"github_repository_issues", inputs:[...]}
  （注意：这里多了结构化的 provider / tool / inputs 字段，都是本次新增）
  │  （此刻才知道选了哪些工具）
  ▼
[阶段二 Builder] 对每个工具节点：
  · 调用「解析器」传入 provider+tool → 现拉这个工具的详细参数清单
  · 把参数清单（区分 form/llm）渲染成提示词，喂给这个节点的模型调用
  · 模型按真实参数填 tool_parameters
  · 返回后，用解析器拿到的权威值强制覆盖 provider 标识字段（防模型填错）
  │
  ▼
[阶段三 Postprocess] 组装 + 修连线 + 对齐变量 + 校验
  │
  ▼
合法的工作流图
```

### 4.2 「解析器回调」——本次架构上的关键设计

这里有一个绕不开的矛盾：
- 「拉工具详细参数」这个动作必须访问插件服务和租户信息，按分层约定，这属于**服务层**该做的事；
- 但「Planner 到底选了哪个工具」要等阶段一跑完（在**核心**内部）才知道，服务层没法提前查好。

解决办法：服务层不把「数据」传进核心，而是传一个**能查数据的函数**（回调）。核心在阶段二需要时，回调这个函数按需查。

- 类型定义（`tool_schema.py`）：
  ```
  ToolSchemaResolver = 一个函数(provider, tool) -> 该工具的详细参数信息 | None
  ```
- 核心只持有这个函数，**不知道租户是谁、也不碰插件服务**，保持了「纯」。
- 服务层用 `build_tool_schema_resolver(tenant_id, entries)` 造出这个函数，内部：
  1. 空参数直接返回 None；
  2. 命中缓存直接返回（同一次生成里，同一个工具只查一次插件服务）；
  3. 否则调 `list_builtin_tool_provider_tools` 拉参数，按 `form` 精简；
  4. 任何异常都返回 None（查不到就退回通用模板，绝不让生成中断）。

这跟已有的「工具清单」注入是同一个套路，是它的自然延伸。

### 4.3 阶段一：Planner 现在多标注了什么

为了让阶段二能可靠工作，Planner 的输出多了三类结构化字段（都是可选，旧提示词没有也能跑）：

1. **`provider` / `tool`**（仅工具节点）：明确写出选中的是哪个 provider、哪个 tool。
   - 为什么要结构化：过去只在自然语言的「用途」描述里提工具名，阶段二得用正则去抠，不可靠。现在直接给结构化字段。
2. **`inputs`**（每个非起始节点）：声明「我引用了上游哪些变量」，格式 `[["上游节点id", "变量名"], ...]`。
3. **`outputs`**（仅自定义输出的节点，如 code、参数提取器）：声明「我对外暴露哪些变量名」。

**为什么 inputs/outputs 这么设计（变量契约）**：阶段二的各个 Builder 是**并行**跑的，互相看不到对方产出什么变量名。过去每个节点各猜各的上游变量名，猜错就产生「无效变量引用」。现在让 Planner 在阶段一就把「谁引用谁的什么变量」定下来，成为一份**所有节点共同遵守的契约**，并行的 Builder 照着填，自然就对得上。

**谁定变量名**（这是「代码推导为主」的分工）：
- **固定输出的节点**（llm 固定输出 `text`、工具固定 `text/files/json`、知识检索固定 `result`、分类器固定 `class_name/class_id`……）：输出名由**代码**推导，Planner 不用操心，也不许乱改；
- **自定义输出的节点**（code、参数提取器）：输出名只有 Planner/模型知道，所以要它显式声明 `outputs`。

### 4.4 阶段二：Builder 怎么用这些信息

对每个节点，Builder 组装提示词时按节点类型注入不同的「专属段落」，做到「每个节点只看它需要的信息」：
- 工具节点 → 注入「该工具的详细参数段落」（解析器现拉的，见 4.2）；解析器没拉到就退回通用模板；
- 起始节点 → 注入用户输入声明段落；
- llm / 分类器 / 参数提取器 → 注入「照抄选定模型」段落；
- **所有节点** → 注入「变量契约段落」：明确列出「你只能引用这些确切的 `{{#节点.变量#}}`，不许自己编别的名字」。

工具节点还有一步「兜底覆盖」：模型返回配置后，代码用解析器拿到的**权威** provider 标识（provider_id / provider_type / provider_name / tool_name）**强制覆盖**模型填的值。因为模型经常把三段式 provider_id 截断成两段，这一步保证不管模型填得对不对，最终节点里的 provider 标识一定是合法的。

### 4.5 阶段三：组装与结构适配

组装阶段把碎片拼成整图，并做一系列确定性修复。和本次相关的几处：

- **容器节点的内部起点合成**：iteration（对列表每项循环）、loop（循环直到条件满足）这类「容器」节点，内部需要一个隐藏的起点节点（`<容器id>start`），它不是模型生成的，是**代码合成**的；容器内部第一个子节点由这个起点连入。
- **容器非法边过滤**（本次新增，见 5.4）：丢弃模型误生成的「容器 → 自己子节点」这种非法连线。
- **分支句柄修正**（本次增强，见 5.3）：分类器 / 条件分支 / 人工输入这类节点，每个分支的连线要挂在正确的「手柄」上。
- **变量引用修复 + 校验**：把所有 `{{#节点.变量#}}` 收集起来，对照每种节点类型的真实输出做修正；修不了的（指向不存在的节点/变量）在最终校验里报出来。

## 第四部分补充：机制深挖（每个阶段内部到底怎么运作）

上面 4.1–4.5 讲了「数据怎么流」。这一节往下钻一层，把你最关心的几个机制讲透：外部插件信息的完整获取链路、渐进式加载的精确定义、三个阶段各自的内部设计、并发怎么落地、第三阶段的兼容适配怎么做。

### 4A. 外部依赖怎么接进来（插件信息获取的完整链路）

生成器本身不知道「这个租户装了哪些插件、每个插件有哪些参数」。这些信息在系统外部——一个叫**插件守护进程（plugin daemon）**的独立服务里。它们分两条链路接进来，都发生在**服务层**（因为要访问外部服务和租户），核心逻辑层不碰。

#### 链路 A：工具清单（轻，一次性预取，给 Planner）

调用发生在服务层 `_resolve_generation_context`（`workflow_generator_service.py`）：

```
build_tool_catalogue(tenant_id)                          ← core/workflow/generator/tool_catalogue.py
   └─ ToolManager.list_builtin_providers(tenant_id)      ← 枚举这个租户能用的所有 provider
        ├─ 内置 provider：扫本地磁盘目录（与租户无关）
        └─ 插件 provider：PluginToolManager.fetch_tool_providers(tenant_id)
                            └─ HTTP 请求 daemon 的 management/tools 接口
   └─ 对每个 provider 的每个工具，取「名字 + 一句话描述」
   └─ 按 provider 名排序，截断到最多 80 条（_MAX_TOOLS）
```

产出两样东西：
- `tool_catalogue_text`：给 Planner 提示词的纯文本清单（`format_tool_catalogue`）；
- `installed_tools`：一个 `(provider, tool)` 的集合，供第三阶段校验「模型有没有编造租户没装的工具」（`installed_tool_keys`）。

**关键点**：这一步在生成一开始就做，是**全量**的（所有已装工具），但每个工具只取「名字+描述」这点信息，所以即使几十个工具也塞得进 Planner 上下文。这就是「第一级」。

#### 链路 B：单个工具的详细参数（重，按需现拉，给 Builder）

这条链路的入口不是「立即执行」，而是服务层造一个**回调函数**交给核心，等核心在阶段二真正需要时才触发：

```
build_tool_schema_resolver(tenant_id, entries)           ← core/workflow/generator/tool_schema.py
   └─ 返回一个函数 resolve(provider, tool)
        触发时（阶段二 Builder 里）才执行：
        └─ BuiltinToolManageService.list_builtin_tool_provider_tools(tenant_id, provider)
             └─ 就是你在画布上拖工具节点、选中某工具时，前端渲染参数表单调的同一个接口
             └─ 内置工具读本地声明；插件工具请求 daemon 取参数（含运行时动态参数）
        └─ 在返回的工具列表里按 name==tool 找到目标工具
        └─ 取它的 parameters（逐个用 _trim_parameter 精简）+ output_schema
        └─ 组装成 ToolSchemaInfo 返回
```

`_trim_parameter` 的精简规则（决定「哪些参数要生成器填」）：
- `form == "schema"`（安装期元信息）→ **丢弃**；
- `form == "form"`（用户/生成器要填的）→ **保留**，标 `form`；
- `form == "llm"`（运行时模型填的）→ **保留但标 `llm`**，告诉 Builder「列出来但别填」；
- 每个保留的参数只留：name / type / required / form / description（+ 有则带 default / options）。

**为什么用回调而不是直接查**：见 4.2——「选了哪个工具」要阶段一跑完才知道，服务层没法提前查。回调让「查」这个动作延迟到阶段二、且只查被选中的工具。

#### 两条链路的失败降级
- 链路 A 整体失败（daemon 连不上）：`tool_catalogue_text` 为空、`installed_tools` 为 `None`（意为"关闭工具校验，别误伤"）、解析器也为 `None`。生成照常进行，只是工具节点没有清单可选、退回通用模板。
- 链路 B 单个工具失败：`resolve` 返回 `None`，那个工具节点退回通用模板，其余节点不受影响。

### 4B. 「渐进式加载」的精确定义

「渐进式加载（progressive / lazy loading）」在这里有确切含义，不是泛泛而谈：

> **同一份数据（工具信息），按「用到多少、才加载多少、且在真正用到的那一刻才加载」的原则分级获取，而不是一开始就把全部细节加载好。**

具体到本项目，体现在三个「不」：
1. **不一次性加载全部细节**：Planner 只拿「名字+描述」（链路 A），不拿参数。因为全量参数会撑爆上下文。
2. **不预先加载所有工具的细节**：只有 Planner 在阶段一**选中**了某个工具，阶段二才去拉**那一个**的详细参数（链路 B）。没被选中的工具，其详细参数从头到尾不加载。
3. **不重复加载**：同一次生成里，同一个工具的详细参数只向 daemon 请求一次（解析器内部带缓存 `cache`），后续引用直接命中缓存。

用一句话对比：**非渐进式**是「进门就把整个仓库搬到桌上」；**渐进式**是「先看目录，点了哪样，才去仓库取那一样，取过的记在手边不再跑第二趟」。

### 4C. 阶段一（Planner）内部设计

**目标**：把自然语言需求，转成一个「骨架」——只有节点清单和连线，不含任何详细配置。

**输入**（拼进 Planner 提示词）：模式（workflow / advanced-chat / auto）、用户指令、工具清单文本（链路 A）、可选的既有图（refine 场景）、可选的理想输出示例。

**内部步骤**：
1. **收紧模型参数**：把温度（temperature，控制随机性）压到 0.2，max_tokens 给一个够用的上限。骨架是短 JSON，要的是稳定、确定，不要发散。
2. **调模型 + 解析**：用一个容错 JSON 解析器（能修掉模型偶尔多写的 markdown 包裹、尾逗号）解析返回。解析失败**只重试一次**，重试时追加一句纠正提示（作为用户消息追加，因为部分模型会忽略追加的系统消息）。
3. **校验骨架结构**：每个节点必须有唯一非空 id、必须有 node_type；连线必须非空、且两端都指向真实存在的节点 id。**结构不合格再整体重试一次**，还不行就报错终止。
4. **决定模式**：如果请求是 auto，就依次看「模型自己回的 mode → 从终端节点类型推断（有 answer 就是对话式、有 end 就是工作流）→ 兜底对话式」。

**本次为插件工具新增的标注**（见 4.3）：工具节点要额外产出结构化的 `provider`/`tool`；每个非起始节点要产出 `inputs`（引用了谁的什么变量）；自定义输出节点要产出 `outputs`。

**产出**：一个 `PlannerResultDict`——标题、描述、模式、应用名、图标、起始输入声明、节点清单、连线清单。骨架一确定，就立刻通过 SSE 推一个 `plan` 事件给前端，让你先看到「正在规划：节点 A → 节点 B → …」，不用等后面慢的阶段二。

### 4D. 阶段二（Builder）内部设计与并发实现

**目标**：给骨架里的每个节点，单独生成它的详细配置。

**为什么能并行**：每个节点的配置是**相互独立**的——节点 A 的 prompt 内容和节点 B 的 code 内容互不依赖（它们之间的「关系」已经在阶段一的骨架和变量契约里定好了）。所以可以同时生成。

**并发怎么落地**（`_run_parallel_node_builders`，`runner.py`）：
1. **算出要建哪些**：refine 场景里标了 `keep`（保持不变）的节点直接复用旧配置，不调模型；其余节点都要建。
2. **共享上下文只算一次**：把整份骨架序列化成一段 JSON（`format_parallel_plan`），每个节点的调用都带上它，这样每个 Builder 都知道「自己在整张图里的位置、上下游是谁」。
3. **线程池并发**：用 `ThreadPoolExecutor` 开一个线程池，线程数 = `min(配置上限, 待建节点数)`，上限来自环境变量 `WORKFLOW_GENERATOR_NODE_BUILDER_MAX_WORKERS`（默认 6）。每个待建节点提交一个任务（`executor.submit(_run_node_builder, ...)`），任务里跑的就是「组装该节点专属提示词 → 调模型 → 解析出 config」。
4. **收集结果**：用 `as_completed` 谁先完成先收谁，存进 `configs_by_id`（节点 id → 配置）。
5. **快速失败（fail-fast）**：任何一个节点的任务抛异常，立刻取消其余还没开始的任务并整体报错。理由：一个碎片坏了，整图就废了，继续跑其它任务只会白白消耗模型额度、拖慢报错。已经在执行中的任务无法中断，会随线程池关闭而自然结束。

**为什么用线程池而不是异步协程**：因为每个 Builder 的核心动作是「调模型」这个 I/O 等待，线程池足以让多个调用重叠等待、缩短总时间；且模型调用是同步接口，用线程最直接。

**单个节点怎么建**（`_run_node_builder`）：按节点类型注入不同的「专属段落」（见 4.4），组装提示词 → 调模型 → 要求返回 `{"config": {...}}`。工具节点在这里触发链路 B（现拉参数）、并在返回后做 provider 标识兜底覆盖。

**产出**：`configs_by_id`，交给 `_assemble_parallel_graph` 拼装。

### 4E. 阶段三（Postprocess）如何做到兼容性适配

「兼容性适配」在这里指两件事：**（1）适配 Dify 画布/运行时对图结构的硬性要求**（不管模型吐成什么样，都要修成画布能渲染、运行时能跑的合法结构）；**（2）适配各种节点类型的差异**（每种节点的输出变量、连线手柄规则都不同，要分别处理）。它默认「模型产出的图是坏的」，用一连串确定性修复把它修好。

按执行顺序：

1. **ID 规范化**：Dify 运行时的变量占位符只认 `[a-zA-Z0-9_]` 的节点 id。模型爱写 `node-1`、`node.2` 这种，全部清洗成合法字符，并连带改掉所有引用（连线的两端、parentId、`{{#…#}}` 占位符、`["node","var"]` 选择器）。撞名时加数字后缀，绝不把两个节点合并。
2. **多检索合流**：如果多个知识检索节点同时接进一个 llm、但 llm 只选了其中一个做上下文，插入一个模板节点把多个结果合并。
3. **坐标布局**：用拓扑排序（Kahn 算法）+ 最长路径给顶层节点算坐标——x = 拓扑深度、y = 同层泳道。这样分支会排成平行的行，而不是叠在一起。容器内部节点保留模型给的相对坐标。
4. **补节点默认值**：每个节点补齐画布必需的外层字段；工具节点必补空的 `tool_parameters`/`tool_configurations`（防前端某个校验器空指针崩溃）。
5. **分支手柄修正**（适配分支类节点差异）：条件分支 / 分类器 / 人工输入这三类节点，每个分支的连线要挂在对的「手柄」上。本次增强了两重修：先把「用名字当手柄」的改回「用 id」（见 5.3），再把「落到默认手柄」的按未用手柄补齐。
6. **连线去重 + 采 id + 补类型/容器标记**：去掉重复连线；给每条线补上两端节点类型（画布渲染需要）；判断连线是否在容器内部，打上对应标记。
7. **变量引用修复**（适配各节点输出差异）：收集所有 `{{#节点.变量#}}` 和选择器；对照每种节点类型的**真实输出规则**（llm→text、code→自定义 outputs、分类器→class_name/class_id……，这套规则写在 `_declares_variable` 里，覆盖近 20 种节点）判断引用对不对；指向起始节点但没声明的变量→自动补进起始节点；指向某节点但写错名、而该节点恰好只有一个输出→自动改成那个唯一输出；有歧义的不猜，留给校验报错。
8. **文件类起始变量补全**：file / file-list 类型的起始变量补齐必需的上传配置，否则 Studio 拒绝加载草稿。
9. **容器非法边过滤**（本次新增，见 5.4）：丢弃「容器 → 自己子节点」的非法连线。

修完之后是**最终结构校验**：起始节点恰好一个、按模式要有对应的终端节点（工作流要 end、对话式要 answer）、连线两端都存在、无环、容器拓扑合法、工具都是租户装过的（对照链路 A 的 `installed_tools`）、变量引用都能解析。发现问题就带**机器可读的错误码**返回（前端据此显示本地化提示），但**图照样返回**，方便你看到问题在哪、手动救。

**为什么这一整套叫「兼容性适配」**：模型只懂「语义」（这个流程该有哪些步骤），不懂 Dify 画布和运行时的「格式规矩」（id 字符集、手柄命名、容器入口、变量输出名、坐标……）。第三阶段就是把模型的语义产物，翻译并修正成完全符合 Dify 规矩的结构，让「AI 生成的图」和「你手画的图」在数据层面完全一致、走同一个保存接口、在同一个画布上渲染。

## 第五部分：一路排查出来的真实问题与修复

以下每个都是在真机调试「GitHub Issue 智能分诊」这个复杂案例时暴露、并逐个修掉的。

### 5.1 环境问题：插件服务版本过旧（非代码问题）

**现象**：模型列表、工具列表大量接口返回 404，「很多功能起不来」。
**原因**：插件守护进程容器还是三周前的旧版本（0.6.3），而后端代码需要的接口在新版本（0.6.10）才有。
**处理**：拉取 0.6.10 镜像、用正确的 project 名重建该容器。插件数据挂载在本地目录，重建不丢。
**说明**：这不是本次代码引入的问题，是本地环境版本没对齐。

### 5.2 provider_id 被截断 → 画布崩溃

**现象**：生成含 GitHub 工具的工作流后，画布直接渲染失败爆炸。后端报 `Invalid plugin id langgenius/github`。
**原因**：插件的 provider_id 应是三段式 `langgenius/github/github`，但模型把它截断成两段 `langgenius/github`，Dify 校验插件 ID 时报错，连锁导致前端渲染崩溃。
**修复**：阶段二 Builder 返回后，用解析器拿到的**权威三段式值强制覆盖** provider 标识字段（`runner.py` 的 `_run_node_builder`）。模型填错也不影响。

### 5.3 分类器分支连不上 → 整块子图断开

**现象**：分类器后面的分支节点全部飘着、连不上。
**原因**：分类器每个分支的连线，「手柄」（sourceHandle，决定连线从节点哪个出口出去）应该用分类的 **id**（如 `1/2/3`），但模型填成了分类的**名字**（如 `"紧急缺陷"`）。画布上出口是按 id 渲染的，连线挂在不存在的名字手柄上，于是整块断开。
**修复**：在分支句柄修复逻辑里增加「名字 → id」纠正（`runner.py` 的 `_repair_branch_edge_handles`）。对条件分支、分类器、人工输入三类节点都生效。

### 5.4 容器直连子节点 → 容器子图渲染错乱、终端节点像消失

**现象**：连线看起来没连上、结束节点像是没了。
**原因**：Planner 误生成了一条「iteration 容器 → 它自己的内部子节点」的连线（还带了个非法手柄 `iterator`）。容器不能直连内部子节点（内部入口是合成的起点节点），这条非法连线让整个容器子图渲染错乱，外面的「格式化 → 结束」也跟着显示异常。
**修复**：
- 代码兜底：组装时**自动丢弃**「容器 → 自己子节点」的非法连线（`runner.py` 的 `_assemble_parallel_graph`），入口统一由合成的起点节点承担；
- 提示词预防：在 Planner 提示词里明确禁止写这种连线，减少模型犯错。

### 5.5 变量引用对不上（无效变量）

**现象**：生成后提示「引用了上游未声明的变量」。
**原因**：并行 Builder 各猜各的上游变量名（见 4.3）。
**修复**：引入「变量契约」——Planner 在阶段一声明 `inputs`，Builder 提示词里明确列出可引用的变量，各节点统一用同一套名字。阶段三的启发式修复保留作兜底。

### 5.6 模型幻觉出不存在的系统变量（sys.time）

**现象**：报「引用了不存在的节点 sys」。
**原因**：Workflow 模式下没有系统变量，但模型幻觉出一个 `sys.time`（连合法系统变量都不是）。
**处理**：本次通过提示词约束缓解（明确告知 Workflow 模式无系统变量、要时间就用 time 工具节点）。
